**Abstract**

This report examines test cases, unit tests, and test-driven development (TDD) in order to answer one question: should TDD be applied in every software project? The study is documentary and qualitative, and it draws on eight sources, including the ISTQB Foundation Level syllabus, the JUnit 5 user guide, and an empirical study of the TDD process. The concepts are applied to a case from the course guide, a requirement that grants discounts to frequent customers, which is analysed in two parts. The first part traces the path from requirement to acceptance criterion, test case, and expected result. It identifies ten ambiguities in the requirement and, under assumptions declared by the team, designs twelve test cases, eleven at unit level and one at interface level, using equivalence partitioning, boundary value analysis, and error guessing. The second part describes unit tests, isolation, assertions, and the Arrange–Act–Assert structure. It walks through a red–green–refactor cycle on a small Java example, run with a minimal harness rather than JUnit, and discusses brittle tests and the false sense of security that a passing test suite can create. The conclusion is conditional. TDD is worthwhile when business rules are clear, the code will be maintained and refactored, and the team can work in small, uniform steps. It is less suitable for disposable prototypes, for requirements that are still being explored, or when integration, interface, or performance must be validated. The empirical study suggests that the benefit may come from working in small, uniform steps rather than from writing the test first. However, most of the evidence is normative or based on professional experience, so the conclusion cannot be generalised.

**Keywords:** test cases, unit testing, test-driven development, JUnit 5, boundary value analysis
