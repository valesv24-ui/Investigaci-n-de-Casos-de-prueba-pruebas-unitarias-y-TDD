**Abstract**

This report examines test cases, unit tests, and test-driven development (TDD) in order to answer one question: should TDD be applied in every software project? The study is a documentary, qualitative investigation based on six sources, including the ISTQB Foundation Level syllabus, the JUnit 5 documentation, and an empirical study of the TDD process. The concepts are applied to a small case, a requirement that grants a 10% discount, which is analysed in two parts. The first part traces the path from requirement to acceptance criterion, test case, and expected result, and designs normal, boundary, and error cases using equivalence partitioning and boundary value analysis. The second part describes unit tests, isolation, assertions, and the Arrange–Act–Assert structure, and demonstrates the red–green–refactor cycle with JUnit 5, also discussing brittle tests and the false sense of security that a passing test suite can create. The findings suggest that TDD is worthwhile when requirements are clear, code will be maintained over time, and the team works in small, uniform steps. It is less suitable for exploratory prototypes or for levels of testing beyond individual units. The available evidence is mostly normative and based on professional experience, with limited empirical support, so the conclusion is conditional rather than universal.

**Keywords:** test cases, unit testing, test-driven development, JUnit 5, boundary value analysis
